# 固定 KMNIST 模型的跨建置品質稽核

要回答的問題是：在相同真實單字元資料、初始模型、圖片順序、完整更新預算與化學設定下，普通與競態建置是否得到不同的訓練軌跡和辨識結果，差異是否顯示框架缺陷。原始零 bug 目標與 91 項需求保持。

沿用 chemical-quality-20261013 的五份可重現 driver，從原始檔案指紋確認相同官方 KMNIST。模型是 52 節點、1,248 邊的人工連續核心，不經過 LIF candidate。每組 6,000 張訓練圖片、20 輪、120,000 次更新，三個種子 20260924／20260925／20260926。化學 ON／OFF 的設定保持，共 12 次完整訓練。

## 固定驗收

1. 資料只讀取得，副本放本輪專案暫存。核對六份檔案的大小與 SHA-256、IDX 內容與 CRC、原先宣告的訓練／主要／確認索引。EDA 只讀訓練圖片，不用測試分數調參。記錄框架、driver、協定與 binary 指紋，執行前後核對。
2. 普通與競態各執行既有 driver 控制測試及公開 SDK 等值檢查。對齊初始完整模型、圖片順序與每組可訓練參數量；fixture 或 driver 不符合目前 SDK 時先找根因，不跳過控制或改測試湊結果。
3. 12 次訓練全數保留，無早停、無最好一輪挑選、無改種子。普通／race 成對交錯，時間是各自觀察值而非建置效能主張。模型寫本輪暫存的新路徑，不覆寫原六個模型。程序逾時只視為觀察逾時，沿用 live handle，不重跑。
4. 以每個種子及 ON／OFF 的同圖片預測計算不一致、錯誤互換、準確率百分點及分類損失差。只報三個種子的觀察範圍，不做母體顯著性推論。比較完整參數／最佳化器及逐輪記錄；同建置新程序恢復的完整評分與下一次更新必須精確相同。跨建置的 hash 不同本身不判為 bug，也不預設有品質免責。
5. 若確認框架缺陷，先永久失敗回歸再最小修正，正常模型相容性與重要決策沿用使用者規則。完成必要工程與文件檢查，保存小型證據，刪除自己的快取、資料副本與本輪模型，核對原模型、原資料與其他目錄，依授權提交／推送與讀回。

## 分工與失敗處理

Root 擁有訓練與分析工具、測試、正式程式和共享文件。分工只審資料切分及比較方法，或審原 driver 的實際來源。各 worker 只能寫指定的單一報告，不執行訓練、Go、下載、Git 或記憶寫入，不修改 Root 測試。讀不到來源、指紋不同、輸出不完整或步數不足時，保存失敗並停止該組，不用不完整組合替代完整比較。不同組彼此沒有共享可變模型。

【減法審查】

- Won't List：不換核心、不調參、不增加新公開 API、不宣稱全腦或整頁 OCR。
- 建議移除：本輪重新產生的資料、模型、快取與執行檔，避免重複模型產品留在 repo。
- 建議簡化：沿用原 driver 與分割，只新增建置配對、完整接續及結果分析。
- 需要留意：普通／競態的 source/binary 和時間欄位天然不同，結果比較須分開；不能以連續核心結果消除 LIF 品質未知。
