# LIF 跨建置浮點差異稽核

原始目標是排查會影響模型品質的框架缺陷。上一輪已將差異推到共同初始狀態的 Core.Inputs[4][2]，本輪查證最早運算與支援契約，不先改正常演算法。

## 固定驗收

1. 同一份初始參數、編碼後輸入與讀出上游梯度，在公開 Network 與公開 LIF Forward／Backward 分別取得普通／race 的完整輸出、事件、電位與梯度。每份核心梯度必須與本建置 Network 梯度精確相同，否則不能用縮小案例解釋原差異。
2. 若需要私有 trace，只新增 test-only Go overlay 檔案，方法完成後唯讀取得原值。不得改正式 Forward／Backward 方法。保留未插入觀察的控制，檢查觀察沒有隱藏原差異。
3. 以同一 trace／upstream 做獨立取整參考，保存原 operands、順序、bits 與機器碼依據。只有 causal 第一個分歧可稱根因。硬放電不做錯誤的有限差分，依宣告替代梯度核對。規格、Go 語義及實際建置旗標分開判斷，不把一個間距自動列為 bug，也不宣稱品質沒有影響。
4. 明確裁決確認缺陷、正常允許差異或仍待查。若有確認缺陷，先保留永久 RED 回歸，再做最小修正與相容性驗收；重要相容性決策沿用使用者確認規則。保存必要證據，清除本輪 runs/.tmp/lif-float-audit-20261015，核對來源／原模型／原有目錄，按授權提交／推送與讀回。

Root 擁有探針、正式程式及共享文件，分工只寫各自來源審查報告，不改測試、來源、快取或 Git。普通／race 的模型恢復與取消已有上一輪完整證據，不能替代本輪運算根因查證。原始完整 91 項需求與零 bug 目標保持。

【減法審查】

- Won't List：不改正常公式、模型格式或依賴，不新增全圖訓練／OCR 調參或新公開診斷 API。
- 建議移除：只有必要的初始案例、trace 與獨立算術對照，避免先插入每個正式方法的 log。
- 建議簡化：先用公開 LIF API 隔離 float32 邊界，再用方法完成後的唯讀 trace，保留原 binary 對照。
- 需要留意：記錄運算值可能改變程式碼生成，機器碼與原控制必須能對回；模型品質另需實際任務證據。
