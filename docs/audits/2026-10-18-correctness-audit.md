# 框架正確性體檢（2026-10-18）

目的：找出「框架實際行為和文件、註解宣稱不一致」的 bug，並判斷 KMNIST 單字元模型只有 71–73% 是 bug 還是模型能力不足。

方法：不沿用既有單元測試的寫法，另外依文件與註解用 PyTorch 2.14（CPU、自動微分）寫一份獨立參考實作，和框架逐值比對。可重跑的腳本放在 `scripts/reference/`。執行環境為雲端 linux/amd64、Go 1.25.12，原始證據平台是 Apple M3、Go 1.26.5。

## 結論

- 數值核心沒有發現錯誤。連續、LIF、混合、向量核心的前向、反向梯度、AdamW 更新，在數千組隨機設定下都和 PyTorch 一致（float64 部分誤差 ≤ 1e-9，Insyra float32 邊界 ≤ 2e-5）。
- 找到 4 個「行為和文件不符」的 bug，都在外圍的回報、設定檢查與線上學習層，已修正並補回歸測試。
- OCR 73% 不是 bug。PyTorch 複製同一模型逐步損失一致，最終 72.8%；同形狀的一般 MLP 也只有 73–75%。瓶頸是 784 個像素只能經過 28 個輸入節點。

## 需要決定的設計問題

1. **截斷視窗的起點（已決定，兩種都提供）。** 預設維持從序列開頭切（0、w、2w⋯），這和 PyTorch／Keras 常見的固定切段相同，適合每一步都有損失的任務。新增 `Options.TruncationAlign = "end"`，讓最後一段結束在最後一列，只看最後一步損失的任務可回溯完整 w 步。PyTorch 對照涵蓋 407 組位移案例全部一致。
2. **權重衰減作用在儲存值上。** 固定正負號的邊儲存 log 大小，衰減把它拉向 0，等於把權重大小拉向 1；時間常數也被拉向 1。可改成只對自由權重衰減。
3. **神經活動化學來源不能在新個體的第一步執行。** 既有測試把這定為刻意設計（第一步沒有觀測到的活動）。實際用法上必須先空跑一步。

## OCR 單字元模型

| 模型 | 參數量 | 測試正確率 |
| --- | --- | --- |
| 框架，28 輸入節點、24 隱藏（正式設定） | 23,516 | 73.6% |
| 同一模型的 PyTorch 複製（float32 邊界） | 23,516 | 72.8% |
| PyTorch MLP 784-28-24-10 | 22,926 | 74.5% |
| 框架，128 輸入節點、128 隱藏 | 134,784 | 79.35% |
| PyTorch MLP 784-512-10 | 407k | 81.3% |
| 小型 CNN（批次訓練、早停） | – | 89.15% |
| 4 最近鄰 | – | 81.85% |

- 框架與 PyTorch 前 100 次更新的損失相對差 ≤ 5.8e-8，之後只隨 float32 捨入慢慢擴大。
- 隱藏層加大無效，只會更過擬合；輸入節點加寬才會提升。單字元模式把輸入節點數綁在圖片高度（`tasks/ocr/recognizer.go:113-116`），這是品質上限的主因。
- 評估流程（標籤對應、測試切分、無資料外洩、只用最後一列打分）全部檢查無誤。
