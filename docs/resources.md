# 記憶體與執行時間

目前已量測 CPU 人工範例訓練、官方連線表的完整讀取，以及接線圖建構、保存與讀回。**尚無完整果蠅圖訓練的記憶體、速度或達標時間數字。** 以下資料可用於判斷開發與資料檢查成本，不能換算成訓練完整模型需要多久。

## 已量測的工作

2026-09-13，使用通過 Mac／Ubuntu 驗證的 v4 來源建置程式。來源封存 SHA-256 為 `b88dc61a1ce062a1f9ce93311e8252888f4293cd653667eda1c2988a23372141`。每個工作使用三個獨立程序，沒有清除作業系統檔案快取，也沒有隔離其他桌面工作。時間包含程序啟動和輸出，不含編譯與下載。

| 工作 | 環境與設定 | 三次耗時範圍／中位數 | 三次最高程序 RSS |
| --- | --- | --- | --- |
| 人工延遲關聯訓練並保存快照 | Mac Apple M3，16 GiB 統一記憶體，CPU；3 節點、5 個時間步，600 次更新 | 0.048–0.105 秒／0.049 秒 | 22.92 MiB |
| 同一人工範例訓練並保存快照 | Ubuntu 1，約 32 GiB RAM、4 個邏輯 CPU；600 次更新，使用 CPU | 0.144–0.180 秒／0.144 秒 | 19.24 MiB |
| 完整讀取官方 weights Feather | 同一台 Mac，151,856,684 列、2,318 批，逐批檢查 | 2.030–2.239 秒／2.054 秒 | 76.94 MiB |

RSS 是作業系統報告的程序駐留記憶體峰值。此處使用 macOS `/usr/bin/time -l`，其 RSS 單位為 bytes。它和 Arrow allocator 的配置量不同，也不是顯示卡記憶體。每次命令、時間、程式指紋、完整輸出與原始量測日誌見[資源量測紀錄](../evidence/resource-profile-20260913/macos/report.json)，硬體與依賴見 [doctor](../evidence/cpu-reference-20260913/macos-v4/doctor.json)。這是局部觀察，尤其小範例受啟動與系統負載影響，不是效能保證。

Ubuntu 使用 GNU `/usr/bin/time -v`，原始 RSS 乘以 1024 換算成 bytes。三次命令與日誌見 [Ubuntu 量測紀錄](../evidence/resource-profile-20260913/ubuntu/summary.json)。兩平台的硬體、作業系統與程序啟動成本不同，此表不作同等硬體的速度排名。

600 次更新是範例命令的預設學習流程。它不等於三組 seed 加凍結／打亂對照的完整 `examples run delayed`，也沒有操作真實果蠅圖。讀取 weights 的程序則不建立完整訓練圖、不訓練模型。

### 圖檔跨平台驗證（v7 來源，單次量測）

接手修正後，兩平台使用同一份 95 檔來源，以及上節已保存的 664,407,846 bytes 圖檔。CLI 從同次讀取計算整檔 SHA-256，另以 SDK 讀回並保存到新檔，獨立 SHA-256 均與原件相等，原件保持不變。[完整紀錄與重現命令](../evidence/malecns-source-20260913/graph-store-v2/verification.json)

| --- | --- | --- |

各命令只執行一次，未清除快取或隔離其他工作，Mac 部分量測時間另有 Windows 交叉編譯。兩台主機不同，不能作為同等硬體的速度比較。時間包含啟動及輸出，不含編譯。Ubuntu 未重新掃描原始 weights，也未執行 GPU 或模型訓練。

## 訓練記憶體如何估算

用 `N` 表示選入節點數、`E` 表示實際運算邊數、`T` 表示序列長度、`B` 表示同時處理的個體數、`C` 表示每個節點的狀態維度。原始表格列數、突觸接點數與最終運算邊數必須分開，不能直接套用新聞中的神經元或突觸數。

目前純量 CPU 實作使用 float64。在 64 位元平台，每份來源、目標、延遲索引需 `24E` bytes。`learning.NewNetwork` 保存核心與網路設定兩份拓撲，因此目前訓練網路的拓撲為 `48E`。每邊獨立訓練時，權重、梯度、Adam 一階與二階狀態需 `32E`，每參數更新計數另需 `8E`。這些邊相關項目合計是 `88E` 的部分成本，**尚未包含**節點參數、輸入／讀出、參數與快照副本、交易式更新暫存、歷史與 Go 執行環境。完整 Adam 狀態應以所有參數數量 `P` 計算，為 `24P`，不能只用邊數代替。[網路建構](../learning/network.go)、[拓撲與 trace](../dynamics/continuous.go)、[Adam 狀態](../learning/trainer.go)

目前前向 trace 保存電位、輸出及驅動歷史，這三組數值陣列本身占 `8N(3T+2)` bytes。時間係數 `lambda`／`alpha` 另占 `16N`。反向緩衝、輸入與編碼結果、切片表頭及參數副本另計。目前截斷視窗控制梯度可以往前傳多遠，**不會縮短前向已保存的歷史**。不能用截斷視窗替代尚未實作的重算或分塊節省記憶體。

以下只是算術示例，不是硬體需求或已驗證圖規模：

| 假設 | 計入的部分 | 數量 |
| --- | --- | --- |
| `E=15,000,000`，現有 float64 逐邊訓練 | 上述 `88E` | 1.32 GB，約 1.229 GiB |
| 將目前選入圖的 25,563,197 列各轉成一條運算邊 | 上述 `88E`，尚未實作的訓練轉接假設 | 2,249,561,336 bytes，約 2.095 GiB，另計持有原圖與其餘訓練需求 |
| 把官方 151,856,684 列各當一條運算邊 | 同上，未驗證的建圖假設 | 約 12.45 GiB，尚未計入其餘訓練需求 |
| `N=100,000, T=128`，純量 CPU trace | `8N(3T+2)` | 308.8 MB，約 294.5 MiB |
| 未來每邊額外保存兩個 float64 狀態，`E=15,000,000, B=1, T=128` | 只算邊狀態的完整歷史 `16BET` | 30.72 GB，約 28.61 GiB |

最後一列說明局部可塑性或調節若引入逐邊、逐個體的歷史，記憶體可能遠高於只有權重的模型。是否真的需要保存這些歷史，由各機制的反向與重算實作決定。共享參數、降低數值精度、分塊與重算都要各自驗證，目前不能把可能節省的數量當成已支援能力。

## 完整模型會跑多久

目前不知道。固定圖、純量動態的前向與完整反向工作量大致隨 `T(N+E)` 增長，訓練總時間還要乘上更新次數。向量狀態、外圍網路、資料處理、調節與裝置傳輸會改變成本。達到指定成績所需的更新次數則需要實驗，不能只靠運算複雜度推算。

在完整圖實作後，效能驗收需要固定圖視圖、節點與邊數、精度、時間步、序列長度、可訓練群組及啟用機制，再分別量測資料準備、初始化、前向、反向、更新、保存與恢復。記錄多次耗時、峰值 RAM／裝置記憶體、資料與程式指紋。短訓練可以證明執行能力，但學習達標時間必須另外報告。

目前沒有完整的啟動前記憶體估算／拒絕功能，原需求 OPS-06、LRN-02、OPS-07 持續追蹤。`data inspect` 的容量限制只涵蓋讀取流程，不是整個訓練器的容量保證。

## 重現局部量測

依 README 建置後，macOS 可執行：

```sh
run_dir=$(mktemp -d)
/usr/bin/time -l ./bin/coimnet train delayed --steps 600 \
  --checkpoint "$run_dir/example.json" > "$run_dir/result.json" 2> "$run_dir/time.log"
```

Linux 使用 GNU `/usr/bin/time -v`，其 maximum resident set size 單位為 KiB，轉成 bytes 時乘以 1024。每次使用新目錄，連做至少三次，保留全部結果及 `coimnet doctor`。檢查資料時改用 `data inspect` 及實際原件路徑，記錄檔案指紋與快取條件。量測結果和範例快照留在指定目錄，不作使用者的模型發布。
